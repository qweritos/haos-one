## ADDED Requirements

### Requirement: Explicit host and guest utility roles
As an operator, I want host tooling and container runtime services to have distinct names, so that installation instructions and diagnostics make the privilege boundary obvious.

#### Scenario: Acceptance criteria
- **Given** a supported macOS or Windows host
- **When** host networking is initialized, run, diagnosed, or cleaned up
- **Then** the user invokes `haos-one-host init`, `haos-one-host run`, `haos-one-host doctor`, or `haos-one-host cleanup`
- **Given** a HAOS One image
- **When** image contents are inspected
- **Then** the image contains a separate Linux executable named `haos-one-agent` and does not use the host CLI as its guest daemon
- **Given** existing host and guest YAML generated by the preview implementation
- **When** the renamed utilities load that configuration
- **Then** the configuration remains compatible and keys are not regenerated

### Requirement: One always-running guest daemon
As a HAOS One maintainer, I want one native guest daemon to own networking and Supervisor compatibility, so that the image has one lifecycle and no dynamically built compatibility container.

#### Scenario: Acceptance criteria
- **Given** HAOS One starts with or without `/etc/haos-one/desktop-network.yaml`
- **When** systemd reaches the guest service
- **Then** exactly one `haos-one-agent` daemon starts unconditionally without guest-facing subcommands
- **Given** guest network configuration is present
- **When** the daemon initializes
- **Then** it supervises WireGuard, route projection, discovery injection, the Docker API compatibility proxy, dummy NetworkManager, and Supervisor udev migration in one process
- **Given** guest network configuration is absent
- **When** the daemon initializes
- **Then** compatibility services remain active while only WireGuard, routing, and discovery components remain disabled
- **Given** Docker or the system D-Bus is not ready at daemon startup
- **When** the corresponding component initializes
- **Then** it waits and retries independently without delaying healthy networking components or terminating the daemon
- **Given** a component fails after startup
- **When** its supervisor observes the failure
- **Then** the daemon reports the component-specific error and restarts it with bounded backoff while unrelated components continue operating

### Requirement: Native Supervisor compatibility services
As a HAOS One user, I want Supervisor compatibility implemented by the guest daemon, so that startup requires neither a Python service environment nor a nested helper container.

#### Scenario: Acceptance criteria
- **Given** Supervisor connects to `/run/docker.sock`
- **When** the agent proxies requests to `/run/docker-real.sock`
- **Then** it preserves Docker API streaming, chunked bodies, connection upgrades, and hijacked connections while applying the existing create, info, and container-list rewrites
- **Given** the dummy NetworkManager service is enabled
- **When** Supervisor calls its D-Bus interfaces
- **Then** the Go service preserves the existing object paths, properties, methods, fake-Ethernet behavior, and conditional `haoswg0` projection
- **Given** udev shim mode is `auto`, `force`, or `off`
- **When** the agent evaluates or migrates Supervisor
- **Then** it preserves existing user-namespace detection, Docker create mutation, and idempotent Supervisor recreation behavior
- **Given** the udev shim is required inside Supervisor
- **When** the agent injects it
- **Then** only the minimal Python `sitecustomize.py` payload remains because it must execute inside Supervisor's Python process
- **Given** the image and nested Docker state are inspected after migration
- **When** compatibility services are healthy
- **Then** no `dbus-fast` runtime, Python compatibility daemon, dynamically built `haos_one_compat` image, or `haos_one_compat` container exists

### Requirement: Role-specific release artifacts
As a release tester, I want clearly named standalone host downloads and an embedded guest daemon, so that I cannot accidentally run the container executable on the host.

#### Scenario: Acceptance criteria
- **Given** a host-assisted networking release
- **When** release assets are listed
- **Then** raw executables are named `haos-one-host-mac-intel`, `haos-one-host-mac-apple-silicon`, and `haos-one-host-windows.exe` and one `SHA256SUMS` covers all three
- **Given** amd64 and arm64 container images are published
- **When** their contents are inspected
- **Then** each image contains `/usr/local/bin/haos-one-agent`, its single systemd unit, and no `/usr/local/bin/haos-one-host`
- **Given** host and guest binaries are built from one source revision
- **When** compatibility is diagnosed
- **Then** both expose build and relay protocol versions sufficient to identify an incompatible pair

## MODIFIED Requirements

### Requirement: Host-assisted networking activation
As a HAOS One user, I want mounting guest configuration to activate only the networking component of the existing agent, so that networking remains opt-in while compatibility remains automatic.

#### Scenario: Acceptance criteria
- **Given** `/etc/haos-one/desktop-network.yaml` is mounted read-only
- **When** the always-running agent observes a valid configuration
- **Then** it activates host-assisted networking without an environment variable or a second guest service
- **Given** that configuration is absent, invalid, or removed
- **When** the agent reconciles state
- **Then** networking remains disabled or is withdrawn without stopping Supervisor compatibility services

## REMOVED Requirements

### Requirement: Shared host and guest `haos-one-net` executable
As a maintainer, I wanted one executable to contain both host CLI commands and the Linux guest runtime, so that the first preview reused one build target.

#### Removal Rationale
The shared executable obscures the host/guest privilege boundary, increases platform-specific surface area in every artifact, and prevents the guest compatibility runtime from having a clear independent lifecycle.

### Requirement: Nested Python compatibility container
As a maintainer, I wanted a dynamically built Python container to proxy Docker and emulate NetworkManager, so that compatibility could be developed independently.

#### Removal Rationale
The nested image adds boot ordering, build, dependency, and Supervisor-visibility complexity. The same behavior belongs in the always-running native guest agent, except for the minimal Python payload that must execute inside Supervisor itself.
